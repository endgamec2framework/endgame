Overview

Endgame Professional is a mature C2 framework designed for red teams that need deep OPSEC controls, multi-operator collaboration, and evasion capabilities that keep pace with modern EDR/XDR solutions. It ships with a built-in operator GUI, a full REST API, and a rich library of built-in techniques.

The framework is organized around four core concepts:

  • Listeners — server-side inbound handlers (HTTP, HTTPS, mTLS, TCP, SMB, QUIC)
  • Agents — in-memory implants deployed on target systems
  • Tasks — commands dispatched to agents and executed asynchronously
  • Operators — team members with mTLS-authenticated access to the teamserver

Where to begin

Run the installer

Execute ./install.sh on your Linux C2 server. It installs all dependencies, builds the binaries, generates TLS certificates and your first operator profile.

Connect as an operator

Use c2-client -name admin on the same host, or tunnel the operator port over SSH from your workstation.

Create a listener

Open Listeners → + New Listener, pick a protocol and port, and start it.

Build and deploy a payload

Open Payload Builder, configure your listener and OPSEC options, and download the compiled EXE.

Getting Started

Installation

The installer handles all system dependencies, Go toolchain, certificate generation, and first operator profile creation in a single script.

Requirements

  • Debian/Ubuntu or Kali Linux (x86-64)
  • Internet access for initial dependency download
  • Root or sudo privileges
  • License key (contact for access)
ℹ
VPS recommendation — deploy the server on a cloud instance with a public IP. Operators connect via SSH tunnel to the loopback operator API port (default 31337).

Run the installer

bash
git clone git@github.com:endgamec2framework/endgameProfessional.git
cd endgameProfessional
./install.sh

The installer performs these steps automatically:

  1. Installs system packages (git, gcc, mingw, nasm, nmap, impacket, metasploit…)
  2. Installs Go ≥ 1.22, garble, nim + nimble packages
  3. Builds bin/c2-server and bin/c2-client
  4. Builds a default Windows agent (bin/agent.exe)
  5. Generates TLS certificates in certs/
  6. Creates operator profiles in ~/.endgame/profiles/
  7. Downloads SharpCollection .NET tools into data/uploads/

Start the server

bash
./bin/c2-server \
  -http-port 80 \
  -https-port 443 \
  -mtls-port 8443 \
  -operator-port 31337 \
  -quic-port 8444 \
  -db data/c2.db \
  -certs certs \
  -data data

Connect as operator

bash
# On your local workstation — tunnel the operator port first
ssh -L 31337:127.0.0.1:31337 user@your-c2-server

# Then connect
c2-client -name admin -gui-port 9999 -gui-only
# Open http://127.0.0.1:9999 in your browser
Getting Started

Operator Profiles

Every operator authenticates to the teamserver using a mutual-TLS client certificate stored in a JSON profile file.

Profile format

json
{
  "name":            "alice",
  "server":          "127.0.0.1:31337",
  "ca_cert_pem":     "-----BEGIN CERTIFICATE-----\n...",
  "client_cert_pem": "-----BEGIN CERTIFICATE-----\n...",
  "client_key_pem":  "-----BEGIN EC PRIVATE KEY-----\n..."
}

Creating a new operator

Run this on the C2 server (where the CA key lives):

bash
# Via server binary
./bin/c2-server new-operator -name alice -port 31337

# Via the included Python script (no server restart needed)
python3 scripts/gen_operator_profile.py --name alice
⚠
Profile security — the profile contains the operator's private key. Distribute it over an encrypted channel and store it at chmod 600. Never commit it to version control.

Regenerating after a CA rotation

If the server CA changes (e.g. after a reinstall), existing profiles will fail with unknown certificate authority. Regenerate all profiles:

bash
python3 scripts/gen_operator_profile.py --name admin --overwrite
Listeners

QUIC / HTTP3 Listener NEW

The QUIC listener transports beacon traffic over UDP/QUIC (HTTP/3), bypassing TCP-based network inspection and evading many IDS/proxy solutions.

Why QUIC

  • Runs over UDP — most corporate IDS/NGFW solutions only inspect TCP traffic
  • TLS 1.3 is mandatory inside QUIC — no cleartext inspection
  • Firewalls often classify UDP/443 as video streaming (YouTube, Google Meet) and allow it
  • Connection establishment is 1-RTT vs 3-RTT for TCP+TLS — faster initial check-in

Start a QUIC listener

bash
./bin/c2-server -quic-port 8444 ...

Or use the + New Listener dialog and select QUIC as protocol.

Automatic HTTPS fallback

Agents built with transport=quic include a fallback mechanism. After 3 consecutive UDP failures, the agent automatically switches to HTTPS and continues beaconing — no operator intervention needed.

BOF

Beacon Object Files

BOFs are COFF x64 object files that execute in the agent's process context with direct access to the Windows API — no injection, no new process.

How BOFs work

When the agent receives a BOF_RUN task, it:

  1. Copies the COFF bytes into a new RWX memory region
  2. Resolves all import symbols against the process's loaded modules
  3. Calls the exported go(char *args, int argslen) function
  4. Captures any BeaconOutput() calls and sends them back as task output
  5. Frees the memory and returns
✓
CS compatibility — Endgame BOFs are compatible with the Cobalt Strike BOF API. Any BOF written for CS will run unmodified, including the beacon.h helper macros.

Installing BOFs

BOFs are installed through the operator client, not the server. Two methods:

  • CLI: bof install /path/to/my.o in the interactive console
  • UI: Settings → 💾 BOFs → Catalog tab → drag-and-drop

Covert Channels

UDC2 — User-Defined C2 Transport

Replace the agent's built-in HTTP transport at runtime with a custom BOF that delivers beacon data over any channel — DNS, ICMP, Slack, named pipes, carrier pigeons.

How it works

When a UDC2_LOAD task is delivered, the agent:

  1. Loads the COFF into memory and resolves its imports
  2. Replaces its internal http.RoundTripper with udc2RoundTripper
  3. On every beacon cycle, packs the HTTP request body as a binary BOF argument and calls the BOF's go() function
  4. The BOF sends the data over its custom channel and returns the server response via BeaconOutput
  5. The agent decrypts the response normally — the transport layer is fully opaque

Writing a UDC2 BOF

A UDC2 transport BOF exports a standard go(char *args, int argslen) entry point. The agent passes the beacon HTTP body as binary argument data.

c
#include <windows.h>
#include "beacon.h"  // standard CS/Endgame BOF API

void go(char *args, int argslen) {
    datap parser;
    BeaconDataParse(&parser, args, argslen);

    int   dataLen = 0;
    char *data = BeaconDataExtract(&parser, &dataLen);

    // --- send `data` (dataLen bytes) over your custom channel ---
    // e.g. DNS exfil, ICMP, HTTP to a redirector, named pipe...
    char *response = my_custom_send(data, dataLen);
    int   respLen  = my_custom_recv(response);

    // Return the server's response
    BeaconOutput(CALLBACK_OUTPUT, response, respLen);
}
⚠
The BOF stays resident — unlike a regular BOF which is freed after execution, the UDC2 BOF remains loaded for the lifetime of the agent process. Design accordingly: avoid heavy allocations that won't be freed.
Evasion & OPSEC

Obfuscation Pipeline

Apply an ordered chain of encoding and encryption steps to the agent shellcode at build time. The agent decodes in reverse order at runtime before executing.

Available steps

StepDescriptionNotes
sgnShikata Ga Nai polymorphic x64 encoderOutput is larger; breaks static signatures
xorXOR with a random 4-byte key (prepended)Fast; simple but effective against static AV
zlibzlib compressReduces size; changes byte distribution
b64Base64 encodeUseful before network transport
aesAES-256-GCM encrypt with per-build keyStrong; requires ObfuscationKey build var

Configuring a pipeline

In the Payload Builder, open the OPSEC tab and select a preset or enter a custom pipeline:

text
# Preset: Aggressive (maximum evasion, larger payload)
sgn,xor,zlib,aes

# Preset: Balanced
xor,zlib,b64

# Preset: Minimal (fast, small)
xor,b64

The pipeline string is injected as an ldflags build variable (ObfPipeline). The agent reads it at startup and applies pipelineDeobfuscate() before shellcode execution.

Malleable C2 — Live Profile Push

Update a running agent's HTTP communication profile without redeployment. Change the User-Agent, beacon URIs, and custom headers in real time to adapt to network defenses.

Push a profile update

Right-click any agent → 📡 Push Profile, or use the API:

bash
curl -X POST https://127.0.0.1:31337/api/agents/{id}/push-profile \
  --cert ~/.endgame/certs/client.crt \
  --key  ~/.endgame/certs/client.key \
  -d '{
    "user_agent":   "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36",
    "beacon_uris":  "/search,/api/v1/data,/cdn/assets",
    "http_headers": "X-Request-ID: {guid}\nAccept-Language: en-US,en;q=0.9"
  }'

How it works

Each server runs a 30-second background sync goroutine that fetches /api/agents from every configured peer. Peer agents are merged into the local inventory with a peer:{name}:{originalID} prefixed ID and shown with a 🔗 badge in the Agents tab. They are read-only — you cannot task peer agents from your instance.

Adding a peer

Go to Settings → 🔗 Peers

Open the settings panel and navigate to the Peers section.

Click + Add Peer

Enter the peer server's URL and API token. The token is generated on the peer server.

Click Sync

The first sync runs immediately. Peer agents appear in your Agents tab within seconds.

Evasion & OPSEC

Sleep Mask

Between beacon cycles the agent encrypts its own heap and code sections in memory and enters a wait state — making it invisible to memory scanners that run during sleep.

Full heap mask

Endgame's sleepMaskFull() uses VirtualQuery to walk all committed private memory regions and XOR-encrypts each one before calling WaitForSingleObject. On wake-up, regions are decrypted in reverse order before the next beacon cycle executes.

ℹ
Parity with CS 4.11 — the full heap sleep mask matches the Beacon Memory Indicators mitigations introduced in Cobalt Strike 4.9.

Configuring sleep mask

Sleep mask is enabled by default for all agents. To configure the mode:

bash
# In Payload Builder → OPSEC tab
Sleep Mask: Full heap (recommended)
           Code section only
           Disabled
